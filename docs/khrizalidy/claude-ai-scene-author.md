**Для агентов движка moood и анимации: что нужно агенту-автору сцен (Claude в облачной песочнице), чтобы ему было удобно работать**

**1. Сетевые ограничения песочницы (важно для архитектуры)**
- Из shell агента доступны только GitHub (github.com, api.github.com, raw.githubusercontent.com; git clone/push работают), реестры пакетов (npm, PyPI, crates, Go, jsr) и Anthropic. **moood.compl.dev из shell закрыт** (403 на уровне прокси, авторизация не поможет). gist.github.com тоже закрыт.
- MCP работает: он идёт не через shell.
- Всё, что агент отправляет в MCP, он пишет токенами, а всё, что получает, попадает ему в контекст. Поэтому большие файлы через MCP целиком гонять дорого.
- Агенты в других окружениях (локальный Claude Code и т. п.), скорее всего, увидят moood напрямую. **MCP — основной интерфейс, GitHub — дополнительный путь** для песочниц.

**2. GitHub как транспорт** (организация уже создана)
- GitHub App в организации. Создаёт репозитории (на личном аккаунте App этого не умеет — поэтому организация).
- Один репозиторий не годится: доступ на чтение там только на весь репозиторий, разграничить по папкам нельзя, а у пользователей приватные игры.
- Предпочтительно: **временный приватный репозиторий на сессию редактирования.** `begin_editing` (или отдельный `begin_repo_session`) создаёт репозиторий с файлами мира или сцены и выдаёт токен установки, ограниченный этим одним репозиторием (живёт около часа). Агент клонирует, правит, пушит. Вебхук на push отправляет изменения в moood, тот валидирует и рендерит. По commit или таймауту репозиторий удаляется. Данные живут в moood.
- Альтернатива — постоянный репозиторий на мир, тоже создаётся автоматически.
- Результат push (ошибки, ссылки на рендер) агент должен получить через MCP, например `repo_session_status`.

**3. Инструменты MCP для файлов** (модули и сцены)
- `list_files(world)` — дерево, размеры, версии.
- `get_file(path, from_line?, to_line?)` — целиком или кусок.
- `search_file(path|world, pattern)` — где что лежит, с номерами строк.
- `outline_file(path)` — функции и секции с номерами строк.
- `put_file(path, content)` — целиком, для новых и маленьких файлов.
- `patch_file(path, old_text, new_text)` — замена точного куска (как Edit), плюс вариант по диапазону строк. Это основная операция.
- `put_file_from_url(path, url)` — сервер сам скачивает файл с raw.githubusercontent.com, и агент передаёт только ссылку.
- `file_history(path)` / `revert_file(path, version)` — история и откат, как у сцен. Правка общего модуля задевает все сцены.
- Для сцен то же самое: `patch` по id элемента и точечная замена внутри кода одного элемента.

**4. Формат: код не в строках**
- Сейчас JS-код элемента лежит в JSON строкой с `\n` и экранированием. Это главная боль: правки дорогие, ошибки экранирования, точечная замена плохо попадает.
- Нужно, чтобы код был кодом: сцена как папка (`scene.json` с метаданными и `elements/<id>.js`) или сцена как JS-модуль с настоящими функциями. YAML как таковой не нужен.
- Подключение общих модулей явное (импорт по имени и версии). `draft` и рендер показывают, какие модули подключены.

**5. Локальный рендерер в npm**
- Пакет, например `@moood/render`: `render(sceneDirOrSpec, {aspect, time, state, modulesDir}) → PNG + список ошибок`. Плюс CLI.
- Без сети: шрифты и всё нужное внутри пакета. Использует уже установленный Chromium (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`, либо `executablePath: '/opt/pw-browsers/chromium'`), не скачивает браузер.
- Версия рендерера совпадает с версией движка на сайте. Спека или мир указывает версию движка, чтобы локальная картинка была такой же, как на проде.
- Детерминированно: тот же кадр при том же времени и состоянии.

**6. Рендер и ошибки** (и в MCP, и в локальном пакете)
- Рендер в момент `time` (от нуля, а не «через несколько секунд») и с заданным `state`.
- Лист кадров: несколько моментов или состояний в одной картинке. Пакетный рендер нескольких сцен в сетке. «До и после» рядом.
- Ошибки с id элемента, файлом и номером строки. Проверка синтаксиса до рендера. Время на кадр по элементам.
- `scene_summary`: элементы, ключи состояний, направления, длительность таймлайна — без полного спека.

**7. Устойчивость**
- Черновики сохраняются на сервере. После передеплоя сессию можно продолжить без `force` и без пересылки всего спека.

**8. Для совместимости с анимацией** (просто информация)
- В движке полезны общие помощники: плавность (easing), таймлайн или секвенсор вместо абсолютных секунд, общая фигура человека с набором поз (одна качественная, переиспользуемая всеми сценами вместо копий кода в каждом элементе).
- Стиль на уровне мира: палитра, свет, зерно, виньетка, эталонные сцены.
- Сюжетные состояния: таймлайн должен уметь остановиться на развилке, дождаться, пока игра выставит состояние, и продолжить по ветке (`scene.on('change')`).
